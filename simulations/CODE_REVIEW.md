## 1. Критические ошибки (падение или неверный результат)

### 1.1 `bell.py` — `rng` не определён

```python
phase = rng.uniform(0, 4 * np.pi, N_samples)   # NameError
```

Нет строки `rng = np.random.default_rng(seed)`. Скрипт не запускается вообще.

Плюс: `np.random.default_rng()` без seed — результат невоспроизводим. Нужен явный seed.

### 1.2 `lib/plot.py` — `init()` игнорирует три из пяти своих аргументов

```python
def init(title, zoom, elev, azim, size=SIZE, theme='Dark'):
    SIZE = size                                   # ← локальная переменная, нет `global`
    ...
    ax.set_box_aspect([1,1,1], zoom = 4)          # ← хардкод 4, аргумент zoom не используется
    ax.view_init(elev = 30, azim = -45)           # ← хардкод, аргументы elev/azim не используются
```

Три последствия:

* `Electron.py` передаёт `azim=45`, а получает `azim=-45`. Ракурс всегда один и тот же.
* `SIZE = size` пишет в локальную переменную. Модульная `plot.SIZE` навсегда остаётся `8.0`.
  А `Photon.py` строит всю геометрию от `plot.SIZE` (`R = plot.SIZE/2`, `wave_length = plot.SIZE/num_periods`,
  `window_pi = x_axis * (π/plot.SIZE)`). То есть параметр `size` физически не работает —
  измените его, и фигура «уедет» за границы осей, потому что лимиты осей поставлены по локальному
  `SIZE`, а геометрия — по глобальному.
* Переменная `color` (белый/чёрный по теме) вычисляется и никуда не применяется —
  подписи/оси в светлой теме останутся тёмными по умолчанию.

Исправление: `global SIZE` (а лучше — вернуть размер/хранить его в объекте, а не в модульной
глобали), и реально прокинуть `zoom`, `elev`, `azim`.

### 1.3 `lib/plot.py`, `Arrows.recalc` — деление на ноль для векторов вдоль оси Y

```python
if abs(dx) < abs(dz):
    ux, uy, uz = 1.0, 0.0, 0.0
else:
    ux, uy, uz = 0.0, 1.0, 0.0
n1 = d × u
n1_len = sqrt(...)
nx1 /= n1_len          # ← 0/0 → nan
```

Проверено: для `d = (0, ±1, 0)` условие `abs(0) < abs(0)` ложно → выбирается `u = (0,1,0)`,
который **параллелен** `d`, векторное произведение = 0, дальше `nan` на весь наконечник стрелки.

В `Photon.py` вектор E равен `(0, y, z)`, и в моменты, когда `z ≈ 0` (а это происходит
дважды за период на каждой точке нити), стрелка вырождается в `nan` и просто исчезает.

Правильный выбор опорного вектора — ось с **наименьшей по модулю** компонентой:

```python
ax_ = np.argmin(np.abs([dx, dy, dz]))
u = np.eye(3)[ax_]
```

## 2. Физика и математика

### 2.1 `a1.py` — модель тождественно подгоняется под ответ

Это самое важное замечание по всему каталогу.

**(а) УФ-член сокращается сам с собой.**

```python
C_Gouy           = sqrt3 * log(M_P / M_EW) - 105.81
alpha_inv_static = sqrt3 * log(M_P / M_EW) - C_Gouy
```

Раскрывая: `alpha_inv_static == 105.81` **точно** (проверено численно). Ни планковская масса,
ни электрослабый масштаб, ни `sqrt3` на результат не влияют — вся «УФ-часть петли» это
захардкоженная константа 105.81, записанная так, что выглядит как вывод.

**(б) `k` не «ищется», а решается в замкнутом виде.**

```python
k_adapted = math.sqrt(deficit / qcd_base_thermal)
final_val = alpha_inv_no_qcd + compute_thermal_tensor_gluon(k_scale=k_adapted, ...)
```

`tr_Omega ∝ k²` по построению, поэтому подстановка `k = sqrt(deficit/qcd_base)` **алгебраически
гарантирует** `final_val == CODATA` при любых входных данных. И вывод это подтверждает —
`1/alpha = 137.035999` во всех шести эпохах, до последнего знака. Модель не проверяется,
она решается относительно свободного параметра. Предсказательного содержания в текущем виде нет.

Что можно сделать, чтобы вывод стал осмысленным: зафиксировать `k` (например, `k=1` или
значение, откалиброванное **один раз** на сегодняшней эпохе) и показывать *дрейф* `1/α(factor)`.
Тогда график `1/α` от космологического масштаба станет настоящим предсказанием, сравнимым
с наблюдательными пределами на вариацию α (кварцевые часы, Оклo, квазарные спектры).

**(в) `koide_phase_from_masses` — используется невязка вместо фазы.**

```python
return math.sqrt(best_err), best_phi
...
dg, _ = koide_phase_from_masses(*ms)   # берётся ошибка подгонки, фаза выбрасывается
delta_f_map[f["name"]] = dg / 3.0
```

Функция называется «фаза из масс», возвращает `(невязка, фаза)`, а в `delta_f_map` кладётся
невязка. Если это осознанно — нужен комментарий, потому что читается как перепутанные
возвращаемые значения.

**(г) Перебор по 3600 углам не нужен.** Внутри цикла `norm = sqrt(Σcos²)` вычисляется
3600 раз, хотя это **константа** `sqrt(3/2)` (проверено: для любого φ сумма квадратов трёх
косинусов, разнесённых на 120°, равна 3/2). Более того, вся задача — проекция вектора
`x` на окружность в плоскости Койде — решается аналитически через `atan2`, без перебора,
с машинной точностью вместо шага 0.1°.

**(д) Магические числа без источника:** `105.81`, `delta_deg_global = 11.099`,
`theta_W_deg = 28.71` (табличное значение `sin²θ_W = 0.2312` даёт 28.74°),
`1.56e-11` в списке сценариев, `T_critical = 150 МэВ` при `Lambda_QCD = 200 МэВ`.
Каждое стоит снабдить ссылкой на раздел `theory/`.

### 2.2 `photon_broadening.py` — потерян квадрат в формуле дисперсии, и ω_p занижена на 15 порядков

```python
def dispersion_broadening(L, k2, tau_0, z):
    return tau_0 * (1 + z) * np.sqrt(1 + (k2 * L / (tau_0 * (1 + z))**2))
```

Каноническая формула расплывания гауссова импульса:

τ(L) = τ₀ · √( 1 + (β₂L / τ₀²)**²** )

Квадрата нет. Из-за этого при `β₂ < 0` подкоренное выражение может стать отрицательным
(→ `nan`), а при малом аргументе эффект линеен вместо квадратичного.

Второе: `omega_p = 1e-13` подписано как «реалистичное значение». Реальная плазменная частота
межгалактической среды при `n_e ~ 1e-7 см⁻³` — это `ω_p = 5.64e4·√n_e ≈ 18 рад/с`,
то есть на **15 порядков** больше. С текущим числом `β₂L/τ² ≈ -8e-26`, поэтому
`tau_disp == tau_cosmo` бит в бит: третий столбик на диаграмме дублирует второй,
дисперсии на картинке нет вообще.

Посчитано, как выглядит правильный результат (`L` = 1 млрд св. лет, `τ₀` = 1 фс, `z` = 1):

| n_e, см⁻³ | ω_p, рад/с | β₂, с²/м | τ на выходе |
|---|---|---|---|
| 1e-7 | 17.8 | -1.06e-51 | 5.0e-12 с |
| 2e-7 | 25.2 | -2.12e-51 | 1.0e-11 с |
| 1e-6 | 56.4 | -1.06e-50 | 5.0e-11 с |

То есть эффект **есть и он огромен** — 1 фс расплывается в ~10 пс. Сейчас скрипт его прячет.

Третье: `L = 9.46e24 м` — это ровно 1 млрд св. лет, чему соответствует `z ≈ 0.07`, а не `z = 1`
(`z = 1` — это ~10.8 млрд св. лет). `L` и `z` заданы независимо и противоречат друг другу.
И `c = 3e8` — при 3 значащих цифрах в остальных числах лучше `2.99792458e8`.

Четвёртое: `tau_cosmo` считается, но `tau_total = tau_disp` уже содержит множитель `(1+z)` —
столбики «Космология» и «Общая» измеряют одно и то же. Ось X линейная при разбросе в
4 порядка → нужен `plt.xscale('log')`.

### 2.4 `Neutron.py` — нормировка векторов, которая ничего не делает

```python
tx = cos(phi)*cos(theta); ty = cos(phi)*sin(theta); tz = sin(phi)
t_norm = np.sqrt(tx**2 + ty**2 + tz**2)
tx, ty, tz = tx/t_norm, ty/t_norm, tz/t_norm
```

`tx²+ty²+tz² = cos²φ(cos²θ+sin²θ) + sin²φ = 1` тождественно (проверено численно).
Нормировка — чистый оверхед, тем более что ниже стоит `quiver(..., normalize=True)`.
Тот же блок дублируется в `Proton.py`, `DddBarion.py`, `SpinorSim.py` (там без нормировки).

### 2.5 `SpinorSim.py` — фаза Гуи считается от приближённого z

```python
z_approx = r * np.sin(0.5 * theta)      # приближение
gouy_phase = np.arctan(z_approx / z_R)
phi = 0.5*theta + shift - time_phase + gouy_phase

```

`z_approx` и итоговое `z` — разные величины (расходятся тем сильнее, чем больше `gouy_phase`).

### 3.1 `Electron.py` — 27 отдельных вызовов `ax.quiver()` каждый кадр

**Действие:** заменить цикл на `plot.Arrows`, как в `Photon.py`. Это одна из самых
дешёвых и самых заметных правок во всём каталоге.

### 3.2 `Proton.py` / `DddBarion.py` / `Neutron.py` / `SpinorSim.py` — `remove()` + `quiver()` каждый кадр

Дешевле, чем в 3.1 (0.65–0.91 мс), но всё равно это полное пересоздание объекта
matplotlib на каждом кадре плюс мусор для GC. Тот же `plot.Arrows` решает и это.

### 3.3 `lib/plot.py`, `Arrows.recalc` — скалярный цикл вместо numpy

Внешний цикл `for arrow_idx in range(num)` + внутренний `for s in range(4)`, всё на
скалярах Python. Замер: **0.97 мс/кадр на 85 стрелок**, линейно → ~6.8 мс на 600 стрелок.
`Photon.py` держит две такие коллекции → ~2 мс/кадр только на пересчёт геометрии
при бюджете 16.7 мс (FPS=60).

Всё тело `recalc` векторизуется без остатка: `length = np.linalg.norm(v, axis=1)`,
выбор опорной оси через `np.argmin(np.abs(v), axis=1)`, ортобазис через `np.cross`,
запись зонтиков — broadcast `(N,4,3)`.

**Результат после векторизации** (замер, а не оценка — моя первоначальная оценка
«50–100×» оказалась завышенной: на малых N доминируют накладные расходы numpy):

| Стрелок | Было | Стало | Ускорение |
|---|---|---|---|
| 85 (как в `Photon.py`) | 0.97 мс | 0.19 мс | 5.2× |
| 600 | 6.8 мс (экстрапол.) | 0.49 мс | 14× |

Попутно: `self.paths = self._paths` и работа с `self._segments3d` — это приватный API
matplotlib. Работает, но сломается на смене мажорной версии. Хотя бы закрепить версию
в `requirements.txt` и оставить комментарий.

### 3.4 `a1.py` — `compute_thermal_tensor_gluon` пересобирает матрицы на каждом вызове

`omega_base` (3 матрицы 3×3) копируется и умножается на `k_scale` при каждом вызове,
плюс тройной цикл 3×3×3 на след. Так как `tr_Omega ∝ k_scale²`, достаточно посчитать
`tr_Omega(1)` один раз при импорте и умножать на `k²`. Функция вызывается 12 раз —
не узкое место, но код станет и короче, и честнее (сразу видна квадратичность,
из которой следует §2.1(б)).

Также `koide_phase_from_masses`: 3600 итераций × 3 группы = 10 800 проходов там,
где хватает одного `atan2` (см. §2.1(г)).

## 5. Архитектура и дублирование

`Proton.py`, `DddBarion.py`, `Neutron.py`, `SpinorSim.py` — это **один и тот же файл**
с вариациями в 10–15 строк. Общего кода ~120 строк × 4 копии:

* блок инициализации сцены (`figure` → `add_subplot` → `grid(False)` → три `pane.fill = False`
  → `set_xlim/ylim/zlim` → `axis('off')`) — дословно одинаков;
* генерация каркаса тора (`u`,`v`,`meshgrid`,`X_torus`…) — дословно одинакова,
  и при этом уже есть `lib/torus.Torus.plot()`, который делает ровно это;
* алгоритм переменного шага (`while current_idx < num_points` + `core_metric`) — 4 копии,
  в одной из которых баг §1.5;
* `points → segments` через `reshape/concatenate` — 5 копий.

Из-за этого баг §1.5 живёт только в одной копии, а исправление §1.3 придётся вносить четырежды.

Предлагаемая структура:

```
lib/
  plot.py       # сцена, Segments, Arrows  (уже есть, доработать)
  torus.py      # Torus  (уже есть, использовать везде)
  modes.py      # ← новое: quark_mode(), wave_mode(), adaptive_indices(), to_segments()
  __init__.py   # ← сейчас содержит 2 байта; экспортировать публичные имена
Proton.py       # ← остаётся ~40 строк: параметры + сборка + update()
```

Два уже готовых, но не использованных рычага:

* `lib/plot.Arrows` не используется в `Electron.py` и в четвёрке барионных скриптов —
  а он решает главную проблему производительности (§3.1, §3.2);
* `lib/torus.Torus` не используется в `Proton.py`, `DddBarion.py`, `Neutron.py`, `SpinorSim.py` —
  все четыре генерируют сетку тора вручную.

## 6. Совместимость, оформление, гигиена репозитория

### 6.1 Версия Python

`lib/plot.py:74` использует `type RgbaColor = tuple[...]` (PEP 695) — **только Python 3.12+**.
На 3.11 это `SyntaxError`, и `Electron.py` с `Photon.py` не запускаются вообще.
`Untitled.ipynb` собран на 3.14.6. Нужен явный минимум:

```toml
# pyproject.toml
requires-python = ">=3.12"
```

либо заменить на `RgbaColor = tuple[float, float, float, float]` (обычный алиас, работает с 3.9).

Нет ни `requirements.txt`, ни `pyproject.toml` — при том, что нужны `numpy`, `matplotlib`,
`sympy` (для `CubeSpace.py`) и `PyQt`/`PySide` (для `QtAgg`). Новый человек не соберёт окружение.

### 6.2 Бэкенд matplotlib захардкожен

`matplotlib.use('QtAgg')` стоит в `Proton.py`, `DddBarion.py`, `SpinorSim.py` — и падает,
если Qt не установлен. В `Neutron.py`, `bell.py`, `photon_broadening.py` его нет вовсе —
поведение разное у соседних скриптов. Правильно — не трогать бэкенд в коде, а задавать
переменной окружения `MPLBACKEND`, либо выбирать с фолбэком:

```python
import matplotlib
for backend in ("QtAgg", "TkAgg", "Agg"):
    try:
        matplotlib.use(backend); break
    except ImportError:
        continue
```

### 6.3 Ни в одном файле нет `if __name__ == "__main__":`

Всё исполняется на импорте, включая `plt.show()`. Из-за этого ни один скрипт нельзя
импортировать для теста, переиспользовать функцию или запустить пакетно (например,
отрендерить GIF). Минимальная правка: обернуть тело в `main()` и добавить `argparse`
с флагами `--save out.gif`, `--frames`, `--fps`, `--theme`.

### 6.4 Мусор в репозитории

* `CubeSpace/py` — пустой файл нулевого размера в папке `CubeSpace/`. Явная опечатка
  (задумывалось `CubeSpace.py`, который лежит уровнем выше). Удалить вместе с папкой.
* `Untitled.ipynb`, `Untitled1.ipynb` (**263 КБ**) — безымянные черновики. `Untitled1.ipynb`
  почти наверняка содержит выводы ячеек с картинками; в git это раздувает историю навсегда.
  Переименовать по смыслу и чистить вывод перед коммитом (`nbstripout` или
  `jupyter nbconvert --clear-output`).
* `.ipynb_checkpoints/` не в `.gitignore`.
* `lib/__pycache__/*.pyc` лежат на диске (в `.gitignore` они есть — просто удалить с диска).
* `.gitignore` содержит `.vscode`, но `.vscode/launch.json` и `settings.json` физически лежат
  в дереве. Определитесь: либо конфиги проекта коммитятся (тогда убрать из `.gitignore`
  и держать `launch.json` актуальным — сейчас там только `Photon` и `Electron`, остальных
  11 скриптов нет), либо не коммитятся.

### 6.5 Стиль

* Именование файлов вразнобой: `Proton.py`, `DddBarion.py`, `SpinorSim.py` (CapWords)
  против `bell.py`, `photon_broadening.py`, `a1.py` (snake_case). PEP 8 — snake_case для модулей.
  Заодно `DddBarion` → `DddBaryon` (опечатка в транслитерации), `thorus_spin` → `torus_spin`.
* `a1.py` — имя ни о чём не говорит; по содержимому это `alpha_running.py` или
  `fine_structure_thermal.py`.
* Ни одной аннотации типов в скриптах (в `lib/plot.py` они частично есть).
* Нет ни одного теста. При этом тестируемых чистых функций хватает: `koide_phase_from_masses`,
  `dispersion_broadening`, `get_quark_mode` (замкнутость траектории при `theta = 4π`),
  `Arrows.recalc` (ортогональность базиса зонтика). `pytest` + 20 строк закроют

* Нет `README.md` в `simulations/` — какой скрипт что показывает и как связан с главой
  в `theory/`. Учитывая, что проект строится вокруг `theory/index.md`, перекрёстные ссылки
  «формула → скрипт» напрашиваются.
